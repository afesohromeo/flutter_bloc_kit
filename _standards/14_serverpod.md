# Using the Kit with a Serverpod Backend ⭐

> **Applies to:** apps whose backend is **Serverpod** (Dart full stack) instead of a REST API.
> **Precedence:** where this file contradicts 01–13, **this file wins** for Serverpod apps. Everything not mentioned here applies unchanged: BLoC patterns, naming, barrels, `ResponsiveScaffoldWrapper`, routing, i18n, pagination UI, UI rules, tests.
> **Verified against Serverpod 4.0.3** (October 2026, Plotwatch). Re-check §7 and §9 when Serverpod releases a new major version.

---

## 0. Project setup

### 0.1 Layout
Use Serverpod's standard layout. The kit becomes the Flutter package; nothing else nests:

```
my_app/                         ← repo root (plain repo, NOT generated from the kit template)
├── CLAUDE.md  .claude/  _standards/  doc/
├── my_app_server/              ← generated by Serverpod
├── my_app_client/              ← generated by Serverpod; never edited
└── my_app_flutter/             ← this kit, adapted (§0.3)
```

The kit can also be the repo root with `my_app_server/` inside it ("add Serverpod to an existing app": keep only the server, point `client_package_path` in the server's `generator.yaml` to `packages/my_app_client`, run `serverpod generate`, add the client as a path dependency). Prefer the standard layout: Serverpod's tooling (hot reload, Cloud deploy) assumes it.

### 0.2 Create the project
```bash
dart install serverpod_cli           # Windows: add %LOCALAPPDATA%\Dart\install\bin to PATH
serverpod create my_app --database --auth --webapp --no-redis --no-website
```
Create it in a temporary folder and move the three packages to the repo root. Remove the template's `greetings/` example.

### 0.3 Replace the generated Flutter app with the kit
The generated app is a single `main.dart` calling an example endpoint (no architecture), so nothing is lost:
1. Copy from the kit into `my_app_flutter/`: `lib/` (without `*.freezed.dart` / `*.g.dart`), `test/helpers/`, `Makefile`, `l10n.yaml`, `analysis_options.yaml`.
2. Rename every `package:flutter_bloc_kit/` import to `package:my_app_flutter/`, and `lib/flutter_bloc_kit.dart` to `lib/my_app_flutter.dart`.
3. Dependencies: keep the kit's, **remove `dio`**, add `my_app_client` (path), `serverpod_flutter`, and with auth `serverpod_auth_idp_flutter` + `serverpod_auth_idp_client` (same version as the server).
4. Replace `data/api/config/` with the Serverpod versions (§2.3, §2.4).
5. The developer runs `make codegen` and `make i18n`.

### 0.4 Agent tooling
- `serverpod create --ide claude` installs **28 Serverpod and Relic skills** in `.claude/skills/` (`serverpod-*`, `relic-*`) from Serverpod's skills registry. Use `serverpod-overview` once per session, then the matching `serverpod-*` skill per feature area. **These standards still win** over them (layer folders instead of feature folders; no hand-edited migrations).
- Its root `.gitignore` ignores the **whole** `.claude/` folder. Narrow it to the generated parts so `CLAUDE.md` and `.claude/settings.json` are committed:
  ```gitignore
  .claude/skills/
  .claude/knowledge/
  .claude/settings.local.json
  .mcp.json
  ```
- **The `serverpod` MCP server** (a bridge to a running `serverpod start`): register it in the local, gitignored `.mcp.json`, loaded through `"enableAllProjectMcpServers": true` in `.claude/settings.json`. On Windows `serverpod` is a `.bat`, and VS Code keeps the PATH it started with, so call it by full path:
  ```json
  { "mcpServers": { "serverpod": { "command": "cmd",
      "args": ["/c", "C:\\Users\\<you>\\AppData\\Local\\Dart\\install\\bin\\serverpod.bat",
               "mcp-server", "--server-dir", "my_app_server"] } } }
  ```

### 0.5 Who runs what (developer and agent)
- **The developer runs `serverpod start`**: it generates code, runs the server and the Flutter app, and hot-reloads on file changes. **An agent never starts the server.**
- **The agent runs only the test suites** (`dart test` in the server package, `flutter test` in the app). Every other command is written as a "You run:" step for the developer.
- **`serverpod` MCP tools** only work while `serverpod start` runs; if one says the server isn't running, stop and ask the developer to start it.
  - The agent may use the read-only ones: `tail_server_logs`, `tail_flutter_logs`, `get_flutter_app_dtd`.
  - Tools that change state (`create_migration`, `apply_migrations`, `create_repair_migration`, `hot_reload`, `hot_restart`, `spawn_flutter_app`) are the developer's, unless the developer asks.
- **Never edit generated code:** `my_app_server/lib/src/generated/` and the whole `my_app_client` package are rewritten by the generator. Change the `.spy.yaml` models, the endpoints or `lib/server.dart` instead.
- **Checklist after a change:**
  1. `dart analyze` and `dart format` (developer)
  2. a migration if a model with a `table` changed (developer)
  3. `hot_restart` if the change needs it (developer)
  4. tests (agent)
  5. the agent reads `tail_server_logs` / `tail_flutter_logs`

## Summary of overrides

| Standard | Rule(s) | What changes with Serverpod |
|----------|---------|-----------------------------|
| 01 Architecture | Layer flow | Unchanged (UI → BLoC → Repository → API provider), but the API provider wraps the **generated Serverpod client** instead of Dio. |
| 04 API & repository | `AppApiResponse`, `Data`, `data2` | **Removed.** Endpoints return typed values directly. |
| 04 / 09 | RULE-013 | Repositories return **typed, non-null** results; failures are **thrown**, not returned as `null`. |
| 04 / 09 | RULE-015 | API providers catch **all** errors (`catch (e)`) and convert them with `ApiErrorHandler.handle(e)`. |
| 04 / 09 | RULE-016, RULE-017 | Not applicable (no query maps, JSON bodies or `FormData`). Uploads use Serverpod upload descriptions (§2.4). |
| 05 Models / 09 | RULE-018 → RULE-023 | Apply **only to client-only models**. Shared models are **generated by Serverpod** and used directly. |
| 02 / 13 BLoC handlers | Step 4 (null = failure) | Only where an endpoint can legitimately return nothing (e.g. `findInvitation` → `null`). |
| 02 / 09 | RULE-009 error message | `HttpException400` carries an **error code**; the BLoC sets `errorMessage: e.code.message(LocalizationService.localization)`. |
| 13 Pagination | Repository return type | The server returns a **generated page model per list**; the repository converts it to the client-side `PaginatedList<T>`. Live lists use **last-item-ID** keys (§3.3). |
| *(none)* | Server code | Conventions in §4. |

## 1. Models

### 1.1 Shared models are generated
- Everything exchanged between server and client (entities, enums, page models, exceptions) is defined in **Serverpod model files**, one per type: `my_app_server/lib/src/models/{entity}.spy.yaml`.
  - Serverpod accepts model files anywhere under `lib/` and its template groups them by feature; **we keep the layer folders of §4.1**.
- Serverpod generates the classes for **both** server and client. The app uses them **directly** as domain models: no Freezed copy, no hand-written `fromJson`, no payload builders.
- Generated files are never edited.

```yaml
# item.spy.yaml
class: Item
table: item
fields:
  ownerId: int
  name: String
  description: String?
  status: ItemStatus
  createdAt: DateTime
```

```yaml
# item_status.spy.yaml
enum: ItemStatus
serialized: byName      # Serverpod's default; written to make the intent explicit
values:
  - draft
  - active
  - archived
```

Models that must never change after creation can declare `immutable: true`.

### 1.2 Freezed is still used for
- **BLoC events and states** (02 / 13).
- **Client-only models** that never travel to the server as-is: `PaginatedList<T>`, upload queue items, form drafts. They live in `domain/models/` and follow 05.

### 1.3 Localized enum labels
RULE-023's `label(l10n)` becomes an **extension** on the generated enum, in `shared/extensions/{enum}_extensions.dart`:

```dart
extension ItemStatusX on ItemStatus {
  String label(AppLocalizations l10n) => switch (this) {
        ItemStatus.draft => l10n.itemStatusDraft,
        ItemStatus.active => l10n.itemStatusActive,
        ItemStatus.archived => l10n.itemStatusArchived,
      };
}
```
`fromString` / `toStringValue` aren't needed: Serverpod serializes enums itself.

## 2. Errors

### 2.1 The server sends codes, never text
One serializable exception carries a code from a single enum (mirrors the no-hardcoded-text rule, 12):

```yaml
# app_error_code.spy.yaml
enum: AppErrorCode
serialized: byName
values:
  - permissionDenied
  - itemNotFound
  - itemNameTaken
  # … one value per error case, plus one per auth failure handled (§2.3.1)
```

```yaml
# app_exception.spy.yaml
exception: AppException
fields:
  code: AppErrorCode
  details: String?   # technical detail for logs only, never shown to users
```

### 2.2 Client exception types
Same names as 01 / 02 / 13, so the handler patterns apply as written:

| Exception | Meaning | Created from |
|-----------|---------|--------------|
| `HttpException400` | Business / validation error, **with `AppErrorCode code`** | `AppException`; auth module exceptions (§2.3.1); `ServerpodClientForbidden` (→ `permissionDenied`) |
| `HttpException401` | Not signed in / session expired | `ServerpodClientUnauthorized` |
| `NetworkException` | No connection, timeout | `ServerpodClientNetworkException`; `MethodStreamException` subclasses (streams) |
| `UnknownApiException` | Anything else | Fallback (e.g. `ServerpodClientInternalServerError`) |

### 2.3 `ApiErrorHandler`
```dart
class ApiErrorHandler {
  static Exception handle(Object e) {
    if (e is AppException) return HttpException400(code: e.code);
    final authCode = _authErrorCode(e);           // §2.3.1
    if (authCode != null) return HttpException400(code: authCode);
    if (e is ServerpodClientUnauthorized) return HttpException401();
    if (e is ServerpodClientForbidden) {
      return HttpException400(code: AppErrorCode.permissionDenied);
    }
    if (e is ServerpodClientNetworkException || e is MethodStreamException) {
      return NetworkException();
    }
    return UnknownApiException(e);
  }
}
```
All these classes come from `serverpod_client` and work on web.

#### 2.3.1 Auth module errors
The `serverpod_auth_idp` module throws **its own** serializable exceptions (e.g. `EmailAccountLoginException(reason: invalidCredentials)`), not `AppException`. Give `AppErrorCode` one value per auth failure you handle (`authInvalidCredentials`, …) and map module exception + `reason` to it in `_authErrorCode(e)`. The full list comes from `serverpod_auth_idp_client`.

### 2.4 API provider
```dart
class ItemApiProvider {
  Client get _client => ApiProvider().client;   // the generated Serverpod client

  Future<Item> archiveItem(int itemId) async {
    try {
      return await _client.item.archive(itemId);
    } catch (e) {
      throw ApiErrorHandler.handle(e);
    }
  }
}
```
- `data/api/config/api_provider.dart` holds the single `Client`, created in `AppInitializer.preAppRun()`:
  ```dart
  final client = Client(await getServerUrl())   // serverpod_flutter
    ..connectivityMonitor = FlutterConnectivityMonitor()
    ..authSessionManager = FlutterAuthSessionManager();
  await client.auth.restore();              // saved session, before the first frame
  unawaited(client.auth.initialize());      // validated with the server in the background
  ```
  Restoring before the first frame lets the router guard know at once whether the user is signed in (no flash of the sign-in page).
- **Server URL and public keys:** `getServerUrl()` reads `--dart-define=SERVER_URL=...`, else `assets/config.json` (`"apiUrl"`), else localhost. For the web app, the server serves its own `config.json`, so one build works on every environment. Public client IDs (Google sign-in, web map keys) go in the same file or a `--dart-define`, never in code. Release builds: `flutter build apk --release --dart-define=SERVER_URL=https://<project>.api.serverpod.space/`.
- **Authentication:** the `serverpod_auth_idp` module (email identity provider + JWT with refresh), as set up by the Serverpod 4 template. The legacy `serverpod_auth` module is not used.
- **File uploads:** the server returns an upload description, the app uploads the bytes, the server verifies.
  - Server: `session.storage.createUploadDescription(storageId: …, path: …)`, then `session.storage.verifyUpload(storageId: …, path: …)`.
  - Client: `FileUploader(description).upload(stream, length)` (or `uploadByteData`).

### 2.5 Repository
```dart
class ItemRepository {
  ItemRepository({ItemApiProvider? apiProvider})
      : _apiProvider = apiProvider ?? ItemApiProvider();
  final ItemApiProvider _apiProvider;

  Future<Item> archiveItem(int itemId) async {
    try {
      return await _apiProvider.archiveItem(itemId);
    } catch (e) {
      log('Error archiving item: $e');
      rethrow;                                   // RULE-012 unchanged
    }
  }
}
```

### 2.6 BLoC handler
The 5-step backbone stays; messages come from the code:

```dart
} on HttpException400 catch (e) {
  emit(state.copyWith(
    itemActionStatus: GenericStatus.failure,
    itemActionErrorMessage: e.code.message(LocalizationService.localization),
  ));
} on HttpException401 catch (_) {
  emit(state.copyWith(itemActionStatus: GenericStatus.failure,
      itemActionErrorMessage: LocalizationService.localization.errorUnauthorized));
} on NetworkException catch (_) {
  emit(state.copyWith(itemActionStatus: GenericStatus.failure,
      itemActionErrorMessage: LocalizationService.localization.networkError));
} catch (e) {
  log('ItemBloc._onArchiveItem error: $e');
  emit(state.copyWith(itemActionStatus: GenericStatus.failure,
      itemActionErrorMessage: LocalizationService.localization.errorArchivingItem));
}
```
`AppErrorCode.message(l10n)` is an extension in `shared/extensions/app_error_code_extensions.dart`, with **one ARB key per code** (`errorItemNameTaken`).

## 3. Pagination

### 3.1 One page model per list
Serverpod models can't be generic:

```yaml
# item_page.spy.yaml
class: ItemPage
fields:
  items: List<Item>
  page: int
  pageSize: int
```

Endpoint pattern: `Future<ItemPage> list(Session session, {int? page, int? pageSize, String? keyword})`, with defaults applied **on the server** (see §7, named parameters). Filters and search always run on the server (13).

### 3.2 Repository converts to `PaginatedList<T>`
```dart
Future<PaginatedList<Item>> fetchItems(int pageKey, {String? keyword, int? size}) async {
  try {
    final page = await _apiProvider.fetchItems(pageKey, keyword: keyword, size: size);
    return PaginatedList(content: page.items, pagination: Pagination(size: page.pageSize));
  } catch (e) {
    log('Error fetching items: $e');
    rethrow;
  }
}
```
BLoCs and pages then follow 13 exactly as written.

### 3.3 Live lists (streams)
For lists that receive new items in real time (activity feeds, notifications), page numbers shift and produce duplicates:
- `pageKey` = **ID of the last loaded item** (first page: `0`); the server returns items **older than** it (`WHERE id < :beforeId ORDER BY id DESC LIMIT :pageSize`).
- The UI calls `appendPage(items, lastItem.id)` instead of `appendPage(items, pageKey + 1)`.
- Items from the Serverpod stream are added at the top through a **separate BLoC event** (`liveItemReceived`), de-duplicated by ID.

## 4. Server conventions

### 4.1 Folder structure (`my_app_server/lib/src/`)
| Folder | Contents | Naming |
|--------|----------|--------|
| `models/` | Entities, enums, page models, `AppException` | `{entity}.spy.yaml` |
| `endpoints/` | One endpoint per feature (the template's `auth/` endpoints move here) | `{feature}_endpoint.dart` → `{Feature}Endpoint` |
| `services/` | All business logic | `{feature}_service.dart` → `{Feature}Service` |
| `future_calls/` | Scheduled jobs | `{name}_future_call.dart` → `{Name}FutureCall` |
| `web/` | Web routes (the template's app config route lives here) | `{name}_route.dart` |
| `generated/` | Serverpod output: **never edit** | — |

**Future calls** (Serverpod 4) are typed: a class extends `FutureCall<T>` and declares public `Future<void>` methods taking a `Session` first. `serverpod generate` creates `callAtTime`, `callWithDelay`, `callRecurring().cron(...)` / `.every(...)` and `cancel(identifier)`. Use an `identifier` whenever a call may need cancelling.

### 4.2 Layer rules
1. **Endpoints are thin:** require sign-in → permission check → validate input → call one service method → return.
2. **Services hold the business logic.** Domain services don't call each other; only cross-cutting services (permissions, audit, notifications, activity) may be called from any service.
3. **Errors:** always `throw AppException(code: AppErrorCode.x)`; never plain `Exception('text')`, never error strings.
4. **Transactions:** a write touching several tables runs in `await session.db.transaction((transaction) async { … })`, passing `transaction: transaction` to every call inside.
5. **Money:** integers in minor units plus an ISO 4217 currency code. Never `double`.
6. **Time:** UTC everywhere; trust-relevant timestamps are set by the server.
7. **Migrations:** generated with the CLI, committed, never edited.
8. **Logging:** `session.log(...)`; never passwords, tokens, signed URLs or secrets.
9. **Authentication:** every endpoint requires sign-in by default; public routes are explicit exceptions.

### 4.3 Server tests (TDD)
| Kind | Location | Covers |
|------|----------|--------|
| Integration | `test/integration/{feature}_endpoint_test.dart` | Each endpoint method: happy path, **every permission rule**, every `AppErrorCode` it throws |
| Unit | `test/unit/{feature}_service_test.dart` | Pure logic |

- Integration tests use the generated helper: `withServerpod('Given X endpoint', (sessionBuilder, endpoints) { … })` from `test/integration/test_tools/serverpod_test_tools.dart`; database changes are rolled back after each test.
- Set the caller with `sessionBuilder.copyWith(authentication: AuthenticationOverride.authenticationInfo(userId, {}))`.
- Run `dart test` in the server package. The test database is an embedded PostgreSQL started by Serverpod: **no Docker needed**.

## 6. Deployment
Serverpod Cloud hosts the server, database and file storage. The web build of the Flutter app can be served by the server's web app (`--webapp`).
- `scloud deploy` (in the server package) runs `serverpod generate` and `serverpod run flutter_build` first, which builds the web app into `web/app`. On Windows, `flutter build web --output` doesn't work, so the build script copies with `xcopy`.
- Passwords and secrets live on Cloud (`scloud password set <name> ...`) and in the local `config/passwords.yaml`, never in the repository.
- Static pages the stores and OAuth need (`privacy.html`, `auth.html`) go in the Flutter app's `web/` folder, so they work on `flutter run`, the server-served build and Cloud alike (16).

## 7. Known Serverpod 4.0.3 pitfalls

| Pitfall | What to do |
|---------|-----------|
| A named endpoint parameter **with a default** (`{int page = 0}`) becomes **required** in the generated client | Use nullable named parameters (`{int? page}`) and apply defaults on the server |
| Adding a non-null column to an existing table makes `create-migration` drop and recreate the table | Add new columns as nullable or with `default=`; only use `--force` on tables without data |
| `serverpod start` can rewrite the client even when code generation fails (invalid Dart in an endpoint), removing endpoints from it | Fix the endpoint, then run `serverpod generate` by hand |
| The embedded PostgreSQL (dev and test) keeps running after `dart test` or after closing the `serverpod start` terminal; the next start then fails | Stop the leftover `postgres` processes before starting again |
| `dart install serverpod_cli` installs to a folder that isn't on PATH on Windows | Add `%LOCALAPPDATA%\Dart\install\bin` to PATH; restart VS Code so it sees the new PATH |
| `serverpod create` on Windows prints "Updating Flutter app MacOS entitlements. failed." | Harmless; ignore |
| `FileUploader.upload` / `uploadByteData` **wait forever** when the connection fails (no timeout, the error is swallowed). Seen when a development upload URL pointed at `localhost:8080` from the Android emulator, where `localhost` is the emulator itself | Wrap uploads in `.timeout(...)` and show an error; on the emulator, the PC is `10.0.2.2` |
| The Google identity provider finds users by Google account ID only: a first Google sign-in with the email of an existing password account creates a **second user** | Link by verified email (§9) |

## 9. Google sign-in (serverpod_auth_idp)
**Developer, in the Google Cloud console (Google Auth Platform):**
1. Branding (app name, authorized domains incl. `serverpod.space`), data access (`userinfo.email`, `userinfo.profile`), audience: Testing with test users.
2. Clients: a **Web application** client (needed on every platform: its ID and secret), an **Android** client (package name + debug SHA-1, later the release SHA-1), an **iOS** client (bundle ID, `.plist`).
3. Web client: authorized JavaScript origins = the web app's address; redirect URIs = `https://<web app>/auth.html` and `http://localhost:8083/auth.html` for `flutter run`.
4. Before external testers or reviewers sign in: **Audience › Publish app** (otherwise only test users can).

**Server:** `googleClientSecret` in `config/passwords.yaml` (and `scloud password set googleClientSecret --from-file ...`); `GoogleIdpConfigFromPasswords()` in the identity provider builders; `class GoogleIdpEndpoint extends GoogleIdpBaseEndpoint {}`. Google is on only where the secret is set.

**App:** `client.auth.initializeGoogleSignIn(...)` after `client.auth.initialize()`: on web with `clientId` and `redirectUri: '${Uri.base.origin}/auth.html'`; on phones with `serverClientId` (the web client ID). The ID comes from `config.json`; without it, hide the Google button.

**One account per email (decide it up front):** Serverpod leaves linking to the app. The approach that worked in Plotwatch:
- Google sign-in with a **verified** email that a password account already has → link the Google login to that user (`linkGoogleAuthentication`, in `GoogleIdpEndpoint` before the module's login). Never link an unverified email.
- Email sign-up with an email a Google user already has → refuse with its own error code ("This email is used with Google. Use Continue with Google.").
- Test all four cases on the server: linked, new user, unverified not linked, returning Google user.
